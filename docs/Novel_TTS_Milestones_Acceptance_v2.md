# AI 有声小说阅读器里程碑与验收手册

**版本：V2.0 · 日期：2026 年 11 月 21 日 · 文档状态：实施基线**

本手册用于逐阶段实施和验收 Python + PySide6 有声小说阅读器。桌面平台以 Windows 11 x64 与 Ubuntu 24.04 x86_64 为基线；小说分析采用可配置的 OpenAI 风格接口，支持 OpenAI、DeepSeek 及其他兼容服务；配音提供云端 TTS 与本地 Qwen TTS 两条路径。

实施顺序固定为：**完整 Mock 产品闭环 → 文本与播放可靠性 → 真实小说处理 API → 真实云端 TTS → Windows/Linux 核心应用打包 → 本地 Qwen 最终验证。** 本地模型的权重下载、CUDA 环境安装和真实推理在 M7 开始。M0—M6 使用普通 Python 实现的模拟 worker 提前验证进程协议与故障行为。

下列 52 项验收均为待实施、待测试的目标，不代表已经开发完成或已在用户设备上通过。文中的性能阈值是拟定设备目标；真实结果必须附带运行环境、样本、日志与试听记录。

配套文件：[项目计划书](./Novel_TTS_Project_Plan_v2.md)；[Vibe Coding 指南](./Novel_TTS_Vibe_Coding_Guide_v2.md)。

## 1 固定的架构与交付规则

| 范围 | 实施规则 |
|---|---|
| Qt 主线程 | 负责界面、播放器和轻量 controller，不执行同步网络请求、模型推理、大文件解析或长事务。 |
| 后台任务 | 使用有界 QThreadPool 执行阻塞 I/O 和有限任务，任务携带超时、取消标识与输入修订快照。 |
| SQLite | RepositoryWorker 是唯一写入入口；其连接在所属线程创建、使用、关闭。使用业务事务提交角色、标注、缓存索引和进度。 |
| 小说分析 | 通过 `LLMProvider.analyze_chunk` 调用；Chat Completions 与 Responses 分别适配，按能力选择，不把一种协议固定到一个供应商。 |
| 音频合成 | 通过 `TTSProvider.synthesize` 调用；返回统一 AudioArtifact，来源标记为 `mock_fixture`、`mock_tone`、`cloud` 或 `local`。 |
| 本地真实 TTS | M7 才接入可选运行时。可由 QProcess 启动 FastAPI 控制进程，再以 spawn 启动单 GPU 推理子进程；同时只驻留一个模型、单并发合成。 |
| 本地控制接口 | 仅绑定 `127.0.0.1`，使用随机会话令牌和系统分配端口；不开放公网，不把控制地址写死为固定端口。 |
| 音频交接 | 首版以完整、可校验的音频段交接。Mock 也必须经过实际文件、播放器、进度和缓存链路。 |
| 原文与坐标 | 保留原文快照；领域数据统一使用 Unicode 码点区间，显示时转换成 Qt 文本坐标。 |
| 本地双模型 | 兼容 0.6B-CustomVoice 与 1.7B-CustomVoice；前者不传 `instruct`，后者按有效风格传入。8GB 是目标验证环境，不是预先作出的通过承诺。 |
| 句级定位 | 默认单句独立音频；同人连续短句可合并，但没有可信时间边界时退回独立句合成，不按字数比例制造精准对齐。引导语生成与裁切默认关闭。 |
| 数据与凭据 | 主包不依赖 GPU；密钥不进入代码、日志和导出项目。应用数据、缓存、模型、临时文件与安装目录分开管理。 |

Qt 的线程调用语义、QTextCursor 的 UTF-16 坐标，以及 QMediaPlayer 的异步加载与后端能力需要按锁定版本实现，官方依据见文末参考资料。其余阈值和流程为本项目的验收设计。

## 2 阶段排期与进入条件

按 1 名全职开发者、每周约 5 个有效工作日估算，主体工作为 42 人日，另设 6 人日缺陷缓冲，合计 48 人日，约 10 周。缓冲用于解决实机兼容与阻塞缺陷，不自动扩大功能范围。

| 阶段 | 工作量 | 本阶段交付 | 进入下一阶段的条件 |
|---|---:|---|---|
| M0 工程骨架与契约 | 2 人日 | PySide6 可启动工程、接口 DTO、配置、日志、线程与存储骨架、Mock worker 协议。 | 无 Key、无 GPU、断网时应用可进入；核心包不导入 torch；契约版本明确。 |

| M2 文本 角色与纠音 | 6 人日 | 正式解码与章切分、原文区间、角色身份与声音绑定、人工覆盖、纠音。 | 原文保真、区间校验、自动音色与人工优先规则通过固定样本。 |
| M3 任务 缓存 播放与恢复 | 6 人日 | 队列、取消、修订隔离、局部缓存、倍速预取、崩溃恢复与模拟 worker 故障处理。 | 乱序、迟到、损坏、退出、磁盘不足等故障不破坏已有效数据。 |
| M4 真实多 LLM | 5 人日 | OpenAI、DeepSeek、自定义兼容服务配置，Chat/Responses 适配，预算与质量记录。 | 至少完成 OpenAI 与 DeepSeek 的真实受控验证；契约与原文校验继续生效。 |
| M5 真实云端 TTS | 5 人日 | 云端供应商适配、音色能力、格式归一化、真实费用与错误处理。 | 真实云端声音沿用同一播放和缓存链路；至少主供应商通过完整样书流程。 |

| 缓冲 | 6 人日 | 修复阻塞缺陷、重测受影响场景、整理发行材料。 | 关闭发布阻塞项；不以压缩实机验证换取宣称完成。 |

## 3 证据等级与状态规则

### 3.1 证据必须说明验证了什么

| 证据标签 | 可证明的范围 | 不能替代的验证 |
|---|---|---|
| `MOCK_LOG` | 模拟输入、延迟、乱序、错误与状态转移。 | 真实供应商质量、费用、速率限制与 GPU 性能。 |
| `CONTRACT` | 请求/响应结构、区间覆盖、能力选择、错误映射。 | 服务端实际接受请求或真实音频可听。 |
| `REAL_API` | 指定供应商、模型、端点与日期下的真实调用。 | 其他供应商或其他版本自动兼容。 |
| `REAL_AUDIO` | 使用真实音频设备试听、播放位置与主观听感记录。 | 无声 CI、只检查 WAV 文件存在。 |
| `TARGET_DEVICE` | 特定系统、显卡、驱动、运行时上的实际结果。 | 所有“8GB 显卡”、所有 Linux 发行版。 |
| `PACKAGED` | 从发行包安装运行的结果。 | 开发环境直接运行的通过记录。 |

每次验收报告应引用实际文件路径或报告附件，而不是只填写“已测试”。敏感请求内容与密钥应脱敏；样本使用自制或允许测试的文本和音频。

### 3.2 状态枚举

- **待实施**：尚未有可验证实现。
- **待测**：已有实现但缺少对应证据。
- **通过**：指定范围内的所有条件满足，证据完整。
- **未通过**：已执行验证，存在可重现失败。
- **阻塞**：因设备、凭据或外部服务条件暂时无法执行，写明阻塞原因。
- **不适用**：仅用于明确不属于本次发布范围的可选配置，写明依据；不得用于跳过必选要求。

当前所有 AC 的初始状态统一为“待实施 / 待测”。真实测试表全部保留为“待测”，不得填入估算值伪装成实测。

### 3.3 发布阻塞与性能分档

原文丢失、重复朗读、顺序错乱、跨角色串音、引导语泄漏、过时结果覆盖人工修改、密钥泄漏、数据库无法恢复，以及安装后主流程不可运行均属于发布阻塞项。

性能结果按配置分档：实时播放通过、按章预生成通过、仅合成能力通过、未通过或未验证。某配置只能稳定预生成时，可以交付预生成模式，但不得将其记录为实时播放通过。某模型不能稳定加载时，保留适配与诊断入口，支持清单只列已经通过的配置。

## 4 固定样本与测试环境

### 4.1 样本集合

1. **最小可听样书**：自制 2 章，包含旁白、两个角色、相邻短对白、章节跳转、数字和纠音词，附固定语音 WAV 与 manifest。
2. **文本回归集**：至少 6 章、3 类文风、300 个带原文锚点的人工标注句段；其中包含 150 个可明确归属的对白、30 个歧义对白、30 个初切含多人的父段、30 个极短对白、20 个新角色和 50 项纠音条目。样本允许交集。
3. **格式边界集**：UTF-8、带 BOM 的 UTF-8、GB18030、CRLF/LF、空文件、无章节标题、重复章节标题、补充平面汉字、emoji、ZWJ 字符序列、组合重音、装饰符号与空白行。
4. **长书集**：约百万字的自制或授权文本，用于导入、窗口化显示、随机跳转、内存与重启恢复。
5. **费用样本集**：10 个代表性章节，覆盖对白密集、旁白密集及多人交替，记录每次真实请求与重试成本。
6. **音频边界集**：正常 WAV、空文件、截断 WAV、不同采样率、立体声、损坏文件、极短音频和不受支持格式。

用于调整提示词、预算或切分参数的样本，与最终验收样本分别保留。每套样本记录版本、来源、授权范围及 SHA-256。固定样本变更时注明影响的 AC，不重新声称旧结果覆盖新样本。

## 13 关键 Given When Then 用例

以下用例用于把容易误解的验收目标变成可重复步骤。前置条件必须在测试记录中真实满足；使用 Mock 的用例与真实供应商测试分开归档。

### CASE-01 Mock 必须真实出声

**关联：AC-008、AC-009、AC-011。**

- Given：应用断网、未安装 torch，导入最小样书，选择 `mock_fixture`。
- When：播放样书的旁白和两名角色各一段。
- Then：播放器读取 manifest 对应的真实 WAV；记录实际时长和播放事件；音频设备能听到相应样本；界面显示 Mock；缓存来源为 `mock_fixture`。
- 失败条件：仅定时改变按钮或进度，没有播放真实音频；把 Mock 记作云端或本地模型输出。

### CASE-02 原文坐标跨越补充字符

**关联：AC-012、AC-014、AC-015。**

- Given：原文含 `𠮷`、emoji、组合重音和 CRLF；保存原文快照与码点区间。
- When：点击这些字符后的一句，播放并选中文本纠音，再重开应用。
- Then：高亮与选择范围仍对应同一原文；Qt 坐标由映射得出；重新加载后原文摘要不变；不得切开字形簇。
- 失败条件：将 Python 码点索引直接交给 QTextCursor，导致字符越界或选中错误内容。

### CASE-03 同一段中存在两名说话人

**关联：AC-015、AC-016、AC-019。**

- Given：父段是“林渊说：‘别走。’阿宁回答：‘好。’”，现有林渊，阿宁为新角色。
- When：分析结果返回旁白、林渊对白、旁白、阿宁对白四个连续区间。
- Then：校验完整覆盖原文后，一次事务写入阿宁和音色绑定；按原顺序播放；两个对白不被合成成同一说话人。
- 失败条件：因为句子短而跨角色合并；先写台词后创建角色，形成无效引用。

### CASE-04 手工修改后旧响应到达

**关联：AC-017、AC-021、AC-022。**

- Given：对某句发起自动标注请求 R1；随后用户把说话人改为角色 B 并保存新修订。
- When：R1 迟到并返回角色 A。
- Then：条件提交拒绝覆盖手工结果；角色 B 仍有效；日志可定位被拒绝的旧修订；当前播放不会改回角色 A。
- 失败条件：以“最后响应获胜”替代人工优先与修订校验。

### CASE-05 连续跳句与乱序合成

**关联：AC-020、AC-021、AC-027。**

- Given：第一句合成延迟 5 秒、第二句延迟 1 秒，随后还有可立即返回的片段。
- When：用户连续跳转 20 次，最后停在指定句。
- Then：只有最后有效会话能推动播放器；较早完成的音频不越过原文顺序插播；进度保存到最后实际播放的位置。
- 失败条件：使用完成顺序作为播放顺序，或迟到任务重置播放器 source。

### CASE-06 纠音只影响相关缓存

**关联：AC-018、AC-023。**

- Given：三个已缓存句中只有第二句包含目标纠音词。
- When：修改该词的单书读音并重听整段。
- Then：只有第二句以及确有依赖的合成组重新生成；第一、三句命中缓存；展示原文不变；变更音量/播放倍速的额外合成次数为 0。
- 失败条件：仅因为全局词典版本增加就使整本书所有无关音频失效。

### CASE-07 文件已更名但事务未提交时崩溃

**关联：AC-024、AC-025、AC-029。**

- Given：音频临时文件校验通过，已原子更名，数据库索引事务尚未提交。
- When：强制终止应用并重开。
- Then：原有书籍、角色和进度可用；新文件被识别为孤立文件并按策略清理或恢复；不存在指向不完整音频的成功记录。
- 补充：在“索引已存在但文件被移除”情景中，重开应标记音频缺失并允许重生成。

### CASE-08 删除书籍时仍有请求运行

**关联：AC-022、AC-025。**

- Given：书 A 有运行中的标注与合成任务，书 B 正常可用。
- When：用户删除书 A，随后 A 的结果迟到。
- Then：A 不被后台结果重新创建；A 的派生资源按删除策略清理；B 完全不受影响；旧结果不触碰播放器。
- 失败条件：后台任务凭旧 book ID 再次插入书籍或跳过外键约束。

### CASE-09 云端请求结果未知

**关联：AC-034、AC-035、AC-039。**

- Given：请求已发送，服务端可能已处理，但客户端读取响应时断网。
- When：连接恢复，用户选择重试，或预先配置的有界策略允许重试。
- Then：原请求记录为结果未知；新尝试关联原请求；不把原费用归零；不保证供应商 exactly-once；业务提交仍按内容修订与指纹去重。
- 失败条件：将读超时认定为服务端未执行，并无限自动重试。

### CASE-10 Provider 支持 JSON 但不支持严格 schema

**关联：AC-030、AC-031、AC-032。**

- Given：兼容服务支持 Chat Completions 与 JSON 输出，但不支持严格 schema 参数。
- When：选择该服务分析小说片段。
- Then：按能力发送支持的参数，并在本地进行同样严格的结构与原文校验；非法结构不提交；不能因不支持某参数而自动删除所有校验。
- 失败条件：把 OpenAI 专属参数无差别发给所有兼容服务。

### CASE-11 云端不支持情绪指令

**关联：AC-037、AC-039。**

- Given：某角色有“低声挽留”的剧本风格，所选云端模型没有已确认的指令能力。
- When：合成该句。
- Then：只发送支持的参数；保留剧本风格供其他模型使用；当前音频有效能力明确为未应用该指令；缓存键按实际参数计算。
- 失败条件：界面显示“情绪已生效”，实际请求却忽略该参数。

### CASE-12 双倍速消耗预取缓存

**关联：AC-026、AC-050。**

- Given：已缓冲 20 秒媒体音频，播放速度为 1 倍。
- When：切换到 2 倍速。
- Then：预取调度按约 10 秒墙钟可播时长计算余量；日志显示消耗速率变化；不重新进行 TTS；保调效果按当前后端能力处理。
- 失败条件：仍把 20 秒媒体音频当成 20 秒可继续播放的时间，并据此延迟预取。

### CASE-13 合并短句没有可信边界

**关联：AC-019、AC-027、AC-051。**

- Given：两句同角色短对白允许合并，但供应商没有时间戳，当前也未启用已验证的对齐器。
- When：用户要求点击第二句从该句开始播放。
- Then：默认回到单句独立合成与播放；不按字数比例切音频；旧合并音频不能被伪造为精准对齐产物。
- 失败条件：在无证据情况下标注“逐句精准定位”，实际上跳到前一句或漏掉句首。

### CASE-14 原生 Linux 安装与真实声音

**关联：AC-041、AC-042、AC-043。**

- Given：Ubuntu 24.04 x86_64 原生桌面，普通账户，没有开发环境，存在真实音频输出设备。
- When：安装发行包，将数据目录置于含中文与空格的路径，导入样书并播放、暂停、跳句和倍速。
- Then：界面、字体、路径和声音正常；记录实际 Wayland/X11 会话与音频后端；关闭后无残留进程。
- 失败条件：仅以 WSL2 worker、无头 CI 或源码启动证明原生 Linux 桌面发行包通过。

### CASE-15 最后接入本地双模型

**关联：AC-046、AC-047、AC-048。**

- Given：M0—M6 已通过，本地运行时刚安装，选定目标 8GB GPU；其他 GPU 程序占用已记录。
- When：依次加载 0.6B、1.7B、0.6B，每次预热 2—3 次并合成固定样本。
- Then：始终只一模型常驻；0.6B 请求没有 instruct；1.7B 有效指令可观测；实际模型修订与显存记录完整；切回后不播放另一模型的缓存。
- 失败条件：仅把模型文件下载完成记为模型验证通过，或同时加载两模型导致不必要 OOM。

### CASE-16 GPU 卡死与生成触顶

**关联：AC-028、AC-049、AC-052。**

- Given：控制进程与 GPU 子进程分离，有墙钟时限和一次有界恢复策略。
- When：分别注入 GPU worker 无响应与无法确认正常结束的触顶音频。
- Then：控制进程仍可响应健康与取消；异常音频不进成功缓存；回收旧进程并确认退出后重建；下一条正常任务可以合成和播放。
- 失败条件：只取消 Python 等待协程却宣称 GPU 推理已停止，或将截断结果当作成功音频。

### CASE-17 新音频不能沿用旧断点

**关联：AC-023、AC-027。**

- Given：用户在某句 4 秒处暂停，进度记录包含旧音频指纹。
- When：用户修改该句读音或音色，生成新音频后重开。
- Then：定位到同一原文句，旧指纹不匹配时从新句起点或已验证的安全边界开始；不把旧 4 秒直接套用给新音频。
- 失败条件：新音频变短导致跳过整句，或直接进入下一句。

### CASE-18 本地不够实时但预生成可用

**关联：AC-050、AC-052。**

- Given：某模型在指定设备可稳定生成，但正常预取的 30 分钟测试频繁欠缓冲。
- When：完成该章节预生成，再从正式播放器播放 30 分钟。
- Then：分别记录“实时模式未通过”和“预生成模式通过/未通过”；公布对应 RTF 与等待时间；界面按实际能力提供该模式。
- 失败条件：用已经全部缓存的 30 分钟播放冒充边生成边听通过。

## 14 本地 TTS 性能与听感测量规范

### 14.1 测量前固定条件

记录应用提交号、发行包摘要、样本版本、模型及 tokenizer 修订、Python/PyTorch 版本、CUDA 驱动、注意力后端、精度、GPU 型号、总显存、测试开始时可用显存、桌面及后台 GPU 占用。

同机比较 0.6B 与 1.7B 时使用相同文本、可比音色、1.0 倍速、单并发和相同队列策略。先测无额外指令样本，再为 1.7B 单独增加情绪对白；不能把两种不同任务的耗时混成模型速度对比。

按用户偏好，支持的 Ampere 及以后设备默认开启 TF32 与 cuDNN Benchmark，并保留关闭的 A/B 结果。配置以锁定的 PyTorch 版本支持方式实现，不能混用新旧精度配置接口。若 A/B 显示某配置造成异常或明显回退，应记录原因并形成设备配置覆盖。

### 14.2 样本数量与计时口径

| 测量项目 | 最低执行方式 | 记录内容 |
|---|---|---|
| 冷启动 | 每模型至少 5 次独立启动。 | 加载、2—3 次预热、就绪与首次出声分别计时；全部逐次列出。 |
| 热模型 未缓存 | 已标注的固定样本至少 50 次；覆盖短/中/长句，首音目标单独统计 8—20 字首句。 | 排队、TTS、后处理、落盘、播放器加载及实际出声时间。 |
| 缓存命中 | 至少 50 次，包含启动后和连续播放中的命中。 | 命中查找、播放器加载、实际出声及错误。 |
| 云端尚未标注 | 单独测量并单独统计。 | 云端分析时间、重试、TTS 和首音；不能并入“已标注热首音”。 |
| 长时间播放 | 每模型每目标配置至少一次从空音频缓存开始的 30 分钟正常预取测试。 | 初始缓冲时长、每次欠缓冲、计划停顿与异常停顿、显存曲线、合成总量。 |
| 预生成模式 | 对实时未通过但合成稳定的配置，另测 30 分钟缓存回放。 | 预生成等待时间、播放稳定性、磁盘占用；与实时测试分开。 |
| TF32/Benchmark A/B | 固定模型、样本、精度和后端，仅改变被测配置。 | 冷开销、热延迟、吞吐、峰值显存和异常；避免同时改变多项条件。 |

`RTF = TTS 生成有效音频的墙钟耗时 / 有效音频时长`。有效音频时长不包含播放器额外插入的静音；另报告含排队、后处理和落盘的管线耗时。异步 GPU 测量需在实际测量边界同步，否则 CPU 调用返回时间不能代表 GPU 工作已完成。

首音以用户操作到真实音频设备出声为最终口径；至少用音频回环或可复核的录制抽查。仅记录 `play()` 调用或 `PlayingState` 不足以证明扬声器已经发声。

### 14.3 目标与判定

| 指标 | 拟定目标 | 判定说明 |
|---|---|---|
| 缓存命中首音 | P95 ≤0.5 秒。 | 设备目标；记录样本数和异常点，不删除慢样本美化结果。 |
| 热模型首音 | 已标注、未缓存、8—20 字首句 P95 ≤5 秒。 | 不包含冷加载的比较口径；完整冷启动另报。 |
| 实时生成能力 | TTS RTF ≤0.8。 | 与 30 分钟真实队列测试共同判断，单一平均 RTF 不足以证明连续可播。 |
| 正常预取连续播放 | 30 分钟无 OOM；非计划停顿超过 250 毫秒不多于 1 次。 | 从空音频缓存开始，允许的初始缓冲和水位必须记录；计划标点停顿不计为异常。 |
| 高亮与跳句 | 单句音频对应原文正确；若启用组内可信对齐，抽查起点误差 P95 ≤250 毫秒。 | 未启用可信对齐时采用单句音频，不填写组内对齐“通过”。 |
| 断点恢复 | 同一音频恢复句内位置误差目标 ≤1 秒；指纹改变则按原文安全边界恢复。 | 两种路径分开验收，不把新旧音频时间轴混用。 |
| 正常样本音频完整性 | 漏句、重复、串角色、句尾截断、引导泄漏均为 0。 | 任一出现都必须定位修复并重放受影响集合。 |
| 纠音 | 50 项中至少 45 项回听正确。 | 报告具体失败词和规则；不能仅检查 tts_text 已替换。 |

显存至少记录 PyTorch 已分配峰值、保留峰值与整卡峰值。模型仓库大小、权重文件大小和实际峰值显存分别记录，不用前两者替代后者。

## 16 每阶段交付与最终完成条件

每个阶段结束时提供可运行入口或发行包、所覆盖 AC 的状态表、实际证据、已知问题与下一阶段入口条件。测试脚本、样本 manifest 和报告应随代码版本保存，避免只留下聊天中的“通过”结论。

每次更新只复测变更影响的风险和既定发布门槛，不机械重跑所有无关项目；涉及音频指纹、原文坐标、数据库迁移、队列会话或线程边界的修改应扩大到相关核心用例。

最终交付包括：

1. Windows 11 与 Ubuntu 24.04 x86_64 核心发行包及安装说明。
2. 版本化的核心依赖清单、独立本地推理运行时说明和模型准备步骤。
3. Mock 完整流程、真实多 LLM、云端 TTS、本地双模型各自的证据与能力矩阵。
4. 数据迁移、备份恢复、模型切换、缓存清理及常见故障说明。
5. 52 项 AC 的实际状态、未通过或阻塞项、支持配置与未验证配置。
6. 真实费用记录、目标机性能原始记录、试听报告及完整样本清单。

“本地模型可以合成”“本地模型能持续实时播放”“原生 Windows 推理可用”“原生 Linux 桌面包可用”是四个独立结论。每个结论只在相应证据具备时写入最终发行说明。
